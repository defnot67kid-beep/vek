# VEK 3.x Version and Installer System

VEK 3.0.1 makes `VERSION` the canonical release number. CMake reads it before `project()`, generates `vek/VekVersion.h`, and the Go installer/portable launcher version files are generated by `tools/version_manager.py`.

## Releasing a new version

1. Set the next version once:
   ```bat
   python tools\version_manager.py set 3.0.2
   ```
2. Commit and push the change.
3. Create and push the matching tag:
   ```bat
   git tag v3.0.2
   git push origin v3.0.2
   ```
4. `.github/workflows/release-windows.yml` verifies that the tag and `VERSION` match, builds/tests VEK, and publishes these GitHub Release assets:
   - `VEK-v3.0.2-windows-x64.zip`
   - `VEK-v3.0.2-windows-x64.zip.sha256`
   - `VekInstaller.zip`
   - `VekInstaller.zip.sha256`
   - `release-version.json`

A Git tag by itself is source metadata, not an installable Windows release. The updater deliberately requires verified binary release assets.

## Installer behavior

The installer finds the newest semantic-version tag, checks out that exact tag into `C:\vek\repo`, downloads the matching Windows release package, verifies SHA-256, verifies the package `VERSION`, archives it under `C:\vek\versions\vX.Y.Z\runtime`, and only then deploys the runtime to `C:\vek`.

It no longer writes a newer `C:\vek\VERSION` while copying an older `vek.exe` from the installer package.

If `C:\vek\VERSION` and the actual `vek.exe --version` disagree, the installer reports a **VERSION MISMATCH** and recommends Update or Clean Repair.

## Why v3.0.0 showed VEK 2.8.0

The initial VEK 3.0.0 source had `VERSION=3.0.0` and CMake `project(... VERSION 3.0.0)`, but `include/vek/VekScriptEngine.h` and the GitHub installer still embedded `2.8.0`. The executable was therefore genuinely compiled as VEK 2.8.0 even though the source folder/version metadata said 3.0.0.
